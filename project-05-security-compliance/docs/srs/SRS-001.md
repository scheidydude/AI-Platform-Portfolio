## 1. Introduction

### 1.1 Purpose

This document specifies the requirements for a formal threat model and security control implementation for an enterprise AI assistant deployed in a regulated financial services environment. The system under analysis is a Jira/Confluence AI assistant powered by a large language model (LLM) via AWS Bedrock with tool use capabilities.

This SRS covers:
- The system being threat-modeled (the AI assistant)
- The security controls implemented as a proof-of-concept
- Compliance requirements the system must satisfy

### 1.2 Scope

**In scope:**
- LLM-powered assistant with Jira and Confluence read/write tool access
- AWS Bedrock inference endpoint
- MCP-based tool execution layer
- API gateway and authentication layer
- Logging and audit infrastructure

**Out of scope:**
- The underlying LLM model training or fine-tuning
- Jira and Confluence platform security (treated as trusted with defined interfaces)
- Network-layer security below the API gateway

### 1.3 Definitions

| Term | Definition |
|------|-----------|
| LLM | Large Language Model — the AI model generating responses |
| MCP | Model Context Protocol — tool execution framework |
| Prompt injection | Attack where malicious instructions in user input or retrieved data alter model behavior |
| Trust boundary | Line separating components with different trust levels |
| WORM | Write Once Read Many — storage that cannot be modified after write |
| STRIDE | Threat modeling framework: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege |

## 2. Overall Description

### 2.1 Product Perspective

The AI assistant sits between enterprise users and internal knowledge systems (Confluence, Jira). Users submit natural language queries; the assistant retrieves relevant content, reasons over it, and can take actions (creating or updating Jira tickets) on the user's behalf.

The security system documented here is a layer of controls that wraps this assistant to make it safe for deployment in a regulated financial services environment.

### 2.2 User Classes

| User Class | Description | Trust Level |
|------------|-------------|-------------|
| Enterprise employee | Primary user, submits queries | Low — identity verified by auth layer, claims in prompt not trusted |
| System administrator | Configures assistant, sets session permissions | Medium — operates through admin API, not model context |
| Auditor | Reviews logs and model outputs | Read-only access to audit infrastructure |
| Attacker | External or internal adversary attempting manipulation | Zero trust |

### 2.3 Operating Environment

- Cloud: AWS
- LLM inference: AWS Bedrock (Claude model family)
- Tool execution: MCP servers on Lambda or ECS
- Data sources: Confluence Cloud, Jira Cloud
- Logging: CloudWatch + S3 with Object Lock
- Authentication: Enterprise SSO (SAML/OIDC) via API gateway

## 3. Functional Requirements

### FR-1: Content Isolation

**ID:** FR-1  
**Priority:** Critical  
**Description:** All content retrieved from external sources (Confluence, Jira, web) must be wrapped in explicit trust boundary markers before injection into the model context.

**Acceptance criteria:**
- Every retrieved chunk is prefixed with `[RETRIEVED FROM: {source} | TRUST: external-internal | ID: {id}]`
- Every retrieved chunk is suffixed with `[END RETRIEVED CONTENT]`
- Raw retrieved content never appears in model context without markers
- Markers survive prompt compression/truncation (markers are at chunk boundaries)

**Related:** ADR-002, STRIDE T-1 (prompt injection via document)

---

### FR-2: Output PII Scanning

**ID:** FR-2  
**Priority:** Critical  
**Description:** All model outputs must be scanned for personally identifiable information before delivery to the user. High-risk PII must block delivery; medium-risk PII must trigger a warning.

**Acceptance criteria:**
- Scanner detects: PERSON name, EMAIL_ADDRESS, PHONE_NUMBER, US_SSN, CREDIT_CARD, US_BANK_NUMBER, IP_ADDRESS
- Confidence threshold: 0.7 (configurable)
- High-risk entities (SSN, CREDIT_CARD, US_BANK_NUMBER): action = `block`, response replaced with error message
- Medium-risk entities (PERSON, EMAIL, PHONE): action = `warn`, logged, response delivered with warning header
- Scanner latency < 200ms at p95 for responses up to 4096 tokens
- Scanner result logged with session ID, entity types found, action taken

**Related:** ADR-003, STRIDE I-3 (PII exfiltration)

---

### FR-3: Immutable Audit Logging

**ID:** FR-3  
**Priority:** Critical  
**Description:** Every model interaction must be logged immutably with full attribution.

**Acceptance criteria:**
- Every request logged: user identity, session ID, timestamp (UTC), full input, full output
- Every tool call logged: user identity, session ID, tool name, parameters, result
- Logs stored in S3 with Object Lock in Compliance mode
- Retention: 6 years (FINRA 4511 maximum)
- Log format: structured JSON, queryable by user/session/date
- No log record can be modified or deleted before retention expiry

**Related:** ADR-004, STRIDE R-1 (deniable model actions)

---

### FR-4: Session Permission Immutability

**ID:** FR-4  
**Priority:** Critical  
**Description:** Tool permissions assigned at session initialization cannot be modified by any content in the model context (user messages, retrieved documents, tool outputs).

**Acceptance criteria:**
- Tool permissions defined in session manifest at session start
- Session manifest signed and stored outside model context
- Permission checks performed at tool layer against session manifest, not against model output
- Any model output claiming to grant new permissions is ignored at tool layer
- Attempting to use a tool not in session manifest returns 403, logged

**Related:** ADR-005, STRIDE E-1 (prompt injection to gain tool access)

---

### FR-5: Rate Limiting and Token Budgets

**ID:** FR-5  
**Priority:** High  
**Description:** Enforce hard limits on input length, output length, and tool calls per session.

**Acceptance criteria:**
- Input token limit: 8,192 tokens per request (configurable per team)
- Output token limit: 4,096 tokens per response
- Tool calls per session: 20 maximum
- Rate limit: 60 requests per user per hour
- Exceeding any limit returns 429 with informative error; event logged

**Related:** STRIDE D-1, D-2, D-3

---

### FR-6: System Prompt Hardening

**ID:** FR-6  
**Priority:** High  
**Description:** The system prompt must explicitly define the trust hierarchy, prohibit self-disclosure, and instruct the model to ignore instructions in retrieved content.

**Acceptance criteria:**
- System prompt includes explicit non-disclosure instruction
- System prompt defines the four-tier trust hierarchy
- System prompt instructs model to treat retrieved content as data, not instructions
- System prompt tested against known jailbreak patterns (minimum 10 patterns)

**Related:** ADR-002, STRIDE I-1 (system prompt extraction), STRIDE S-2 (system prompt impersonation)

## 4. Non-Functional Requirements

### NFR-1: Compliance

| Requirement | Framework | Control |
|-------------|-----------|---------|
| Records in non-rewriteable format | SEC 17a-4(f) | S3 Object Lock, Compliance mode |
| Records accessible for examination | SEC 17a-4(f) | Structured JSON, indexed |
| 6-year retention for communications | FINRA 4511 | S3 lifecycle policy |
| Logical access controls | SOC 2 CC6.1 | RBAC at tool layer |
| Restriction of untrusted parties | SOC 2 CC6.6 | Content isolation, trust hierarchy |
| Availability commitments | SOC 2 A1.2 | Rate limiting, token caps |

### NFR-2: Performance

| Metric | Target |
|--------|--------|
| PII scanner latency (p95) | < 200ms |
| Content isolation overhead | < 5ms |
| Audit log write latency (p99) | < 500ms (async, non-blocking) |

### NFR-3: Reliability

- PII scanner and content isolation: no single point of failure — fail closed (block on error)
- Audit logging: async write, failure does not block response but is alerted
- Tool permission check: synchronous, blocks tool call on error

### NFR-4: Maintainability

- PII entity types and confidence thresholds configurable without code change
- Token limits configurable per team via API
- ADR required for any change to trust hierarchy or permission model

## 5. Constraints

| Constraint | Description |
|------------|-------------|
| AWS-only | All infrastructure must run on AWS (Bedrock, S3, CloudWatch) |
| No model fine-tuning | Security controls implemented in prompt engineering and application layer only |
| Regulated environment | Financial services — SEC and FINRA rules apply |
| Existing auth infrastructure | Must integrate with existing SAML/OIDC SSO; cannot replace |

## 6. Acceptance Criteria Summary

The system is considered complete when:

1. All 5 functional requirements have passing automated tests
2. Content isolation and PII scanner implemented as runnable Python code
3. System prompt hardening template passes 10+ jailbreak test patterns
4. Audit log structure validated against SEC 17a-4(f) and FINRA 4511 requirements
5. STRIDE threat model covers all 6 categories with controls mapped
6. All compliance mappings documented with specific framework citations
7. Final INDEX.md links all artifacts
