# SRS-001 — MicroVM Execution Backend with Checkpoint/Restore (Firecracker)

**Project:** P08 — MicroVM Execution Backend with Checkpoint/Restore (Firecracker)
**Version:** 1.0
**Date:** 2026-08-07
**Status:** Draft
**Author:** David Scheiderman

---

## 1. Purpose

This document specifies the requirements for a Firecracker-backed microVM execution layer for Orchid, serving as an alternative isolation backend to [Project 07's](../../../project-07-gvisor-sandbox/) gVisor approach. The distinguishing capability is checkpoint/snapshot/restore for long-running agent tasks — durable execution across failures, not just isolation.

## 2. Scope

**In scope:**
- A stripped-kernel + Alpine rootfs microVM image bootable via the Firecracker API
- A pre-warmed VM pool manager
- Mid-execution snapshot of a running microVM to disk
- Restore of a microVM from snapshot in a new host process
- An end-to-end demo: long-running task snapshotted, host process killed, task resumed with correct state
- Execution API parity with [Project 07](../../../project-07-gvisor-sandbox/), so the two backends are interchangeable from Orchid's perspective
- Orchid FSM integration for triggering checkpoint/restore

**Out of scope:**
- A general-purpose FaaS platform
- Live migration between physical hosts (single NucBox host only)
- Chasing a cold-start target below what the AMD/ROCm homelab hardware actually achieves

## 3. Stakeholders

| Stakeholder | Concern |
|-------------|---------|

| Future engineer (self) | Backend is interchangeable with P07 from Orchid's perspective; host-specific friction is documented, not hidden |

## 4. Functional Requirements

### FR-1 — Minimal MicroVM Boot

**Statement:** A stripped kernel + Alpine (or similar) rootfs image shall boot via the Firecracker API and execute a trivial script.

**Acceptance criteria:**
- MicroVM boots and executes a trivial script; cold start is measured and documented
- Boot time is under 200ms, or documented with an explanation if not — real hardware numbers, not target chasing

**Related:** ADR-003

### FR-2 — Execution API Parity with P07

**Statement:** The Firecracker backend shall expose the same request/response contract as Project 07's gVisor backend.

**Acceptance criteria:**
- Implements `{code, timeout_s, memory_mb, network}` → `{stdout, stderr, exit_code}`
- A test harness can submit the same request to either the gVisor or Firecracker backend and get equivalent results

**Related:** ADR-001

### FR-3 — Pre-Warmed VM Pool Management

**Statement:** A pool manager shall maintain a small number of idle warm VMs, assign them on request, and replenish the pool asynchronously.

**Acceptance criteria:**
- Demonstrated request latency with pool vs. without (cold boot), documented difference
- Pool correctly replenishes after a VM is consumed

**Related:** ADR-002

### FR-4 — Mid-Execution Snapshot

**Statement:** A running microVM's state shall be snapshottable to disk at an arbitrary point during task execution.

**Acceptance criteria:**
- A VM executing a multi-step task can be snapshotted at an arbitrary point
- Snapshot file exists and is documented (size, contents description)

### FR-5 — Snapshot Restore & Task Resumption

**Statement:** A microVM shall be restorable from snapshot in a new host process after the original process is killed, resuming the task correctly rather than restarting it.

**Acceptance criteria:**
- End-to-end demo: task killed mid-execution, resumed from snapshot, completes with correct final state
- Resumed task output matches an uninterrupted run, verified via a deterministic test task

### FR-6 — Orchid FSM Integration

**Statement:** Orchid's lifecycle FSM shall be able to trigger a checkpoint and later resume a task via the restore path.

**Acceptance criteria:**
- Orchid can issue a checkpoint command that results in a snapshot
- Orchid can resume a previously checkpointed task via the restore path, using the existing task metrics/result schema

## 5. Non-Functional Requirements

### NFR-1 — Backend Interchangeability

The Firecracker backend must present the identical execution API contract as P07's gVisor backend, so Orchid can treat them as interchangeable.

**Related:** ADR-001

### NFR-2 — Demo-Scale Pool

The VM pool is sized for demonstration (2–3 warm VMs), not load-tested or sized for production traffic.

**Related:** ADR-002

### NFR-3 — Honest Performance Reporting

Cold-start and pool-latency numbers must reflect actual measurements on the AMD/ROCm NucBox hardware, documented as-is even if targets are missed.

**Related:** ADR-003

### NFR-4 — Host Risk Documentation

Any AMD/ROCm-driver interaction quirks encountered with KVM/Firecracker on this hardware must be documented as findings, not worked around silently.

| Upstream dependency | Reuses P07's execution API contract rather than designing a new one |

## 7. Assumptions

- KVM is available and enabled on the NucBox (confirmed in Phase 0 recon)
- P07's execution API contract is stable before this project's Phase 2 begins
- Phases 4/5 (snapshot/restore) are the highest-risk phases on this hardware and are budgeted accordingly
