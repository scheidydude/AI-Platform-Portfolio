### 2026-08-07 — Phase 1: syscall-interception test complete

- Discovered `docker` group membership doesn't persist across separate tool-call subprocesses (each is a fresh shell) — worked around with `sg docker -c '...'` per invocation rather than relying on a persistent `newgrp` session.
- Wrote `scripts/probe_io_uring.py` (calls `io_uring_setup(2)` via `ctypes`) and `scripts/verify_isolation.sh` (runs both isolation tests across `runc`/`runsc`), committed to the repo as reusable/re-runnable proof artifacts rather than one-off scratchpad commands.
- **Test 1 (kernel identity):** `uname -a`/`/proc/version` return the real host kernel (`6.19.0-061900rc8-generic`) under `runc`, but a fabricated `4.19.0-gvisor` under `runsc` — proves the sentry answers the syscall itself.
- **Test 2 (unimplemented syscall):** `io_uring_setup` returns `EPERM` under `runc` with Docker's default seccomp profile (not yet a kernel-level signal), succeeds (`ret=3`) under `runc` with seccomp disabled (real kernel supports it), and returns `ENOSYS` under `runsc` regardless of seccomp — gVisor's own syscall table simply doesn't implement it. Full output in `findings.md`.
- FR-1 acceptance criterion met. Phase 1 marked complete in `task_plan.md`/`INDEX.md`. Next entry point: Phase 2 — harden `ContainerRunner` with `isolation.container_runtime`/`container_memory_mb`/`container_cpus` config and extend `WorkerResult` additively.

### 2026-08-07 — Phase 3: Squid egress-allowlist sidecar

- Resolved Phase 0's last open item: checked the live systemd Traefik instance and both its dynamic config files directly. Confirmed it's ingress-only (external HTTPS → internal services via `Host()` rules) — no egress/forward-proxy role at all, and no forward-proxy tooling installed on the host. SRS-001 FR-3's "allowlist via Traefik" premise was wrong, same shape as the Phase 0 `TesterAgent` finding.
- Asked David how to implement the allowlist: forward-proxy sidecar vs. DNS-based filtering vs. custom bridge + iptables. **Decision: forward-proxy sidecar** (recorded as ADR-004).
- Built `orchid/sandbox_egress.py`: manages a Squid sidecar dual-homed onto a new `--internal` Docker network (`orchid-sandbox-internal`, no outside route) plus the normal bridge. `ContainerRunner` now always sets `--network` — `none` by default (previously no flag at all, meaning full internet access — a deliberate behavior change per FR-3, not a bug), or the internal network + proxy env vars when `isolation.container_egress_allowlist` is set.
- Unit tests (7 new/updated across `test_sandbox_egress.py` and `test_container_runner.py`) plus the full targeted suite (16/16) and broader 52-test consumer subset — all clean.
- Real end-to-end verification against the actual sidecar, not mocks: default-deny fails DNS resolution entirely; allowlisted `example.com` succeeds over both HTTP and HTTPS; non-allowlisted `wikipedia.org` gets a 403 from Squid's ACL on both protocols; same four cases re-run composed with `--runtime=runsc` from Phase 2.
- **Found a real gVisor limitation along the way:** the first `runsc` + allowlist test failed — not because the proxy was misconfigured, but because `runsc`'s netstack can't resolve names via Docker's embedded DNS server on a user-defined network (confirmed by isolating the exact same lookup: works under `runc`, fails under `runsc`; raw IP works under both). Fixed by having `sandbox_egress.ensure_egress_proxy()` return the sidecar's IP instead of its container name. This is genuine "what gVisor doesn't solve" material for the Firecracker comparison write-up, not a bug to bury.
- Committed to `p07-gvisor-hardening` (`f7e0dbf`). Portfolio docs updated: SRS-001/DESIGN-001 → v1.2, new ADR-004, task_plan.md/INDEX.md/HANDOFF.md all reflect Phase 3 complete.

### 2026-08-07 — Phase 4: consumer regression check + real live end-to-end demo (and 3 more pre-existing bugs)

- Checked `WorkerResult` consumers individually across 9 test files (avoiding the leaky full suite): 8 failures across `test_metrics.py`/`test_providers.py`/`test_rollup.py`, every single one confirmed identical on `main` by checking it out and re-running. Zero regressions.
- Went to run a real live `TesterAgent` demo under `runsc` and hit a wall of pre-existing bugs, none related to gVisor: `_prepare_project` read a `TaskContext` field (`project_path`) that doesn't exist — would `AttributeError` on the first call; it also crashed on any top-level *file* in a project via an unconditional `shutil.copytree`; and — the big one — `ContainerRunner` never mounted anything into the container at all, so `docker run python:3.12-slim python3 -m orchid.worker_subprocess` would always fail with `ModuleNotFoundError: No module named 'orchid'`. Confirmed this last one directly before assuming it.
- Asked David how to handle it, since it's baseline functionality, not gVisor-specific hardening — **decision: fix it.** Added mounts for the project dir, `ORCHID_ROOT` (read-only, so the container gets `orchid` via the same editable install the host uses), and — after another dead end — a uv-managed Python toolchain directory living outside the repo that `sys.executable` resolves through via several layers of symlinks (`pyvenv.cfg`'s `home` field pointed at yet another alias directory a narrower mount didn't cover).
- Got the container importing `orchid` successfully, then hit a fourth gap running the actual agent: zero host env vars reach the container by design, so `LLAMA_BASE_URL` never got there and the LLM call failed. Added `isolation.container_env` — explicit, opt-in, narrow (not a blanket passthrough, to avoid leaking secrets into the sandbox).
- Fifth gap: Squid's `Safe_ports` ACL only allowed 80/443, silently denying the LAN LLM's port (8082) before the domain allowlist was ever checked. Added 8081-8082 to the template.
- With all five fixes in place: full live demo succeeded. Real `TesterAgent` task, `--runtime=runsc`, 512MB memory cap, network locked to exactly `ai.scheidy.com` (the LAN LLM endpoint) via the Squid sidecar — `success=True`, `exit_code=0`, `duration_s=54.08` (real 35B-model inference), `result={"passed": true, "tests_run": 1, ...}`. No orphaned containers afterward.
- Added regression tests for the two `TaskContext`-field/mount bugs; updated the three existing `_build_docker_command()` call sites for its new `project_dir` parameter. Full P07 suite: 18/18. Broader regression check across all 4 consumer modules + P07's own tests: 86/86.
