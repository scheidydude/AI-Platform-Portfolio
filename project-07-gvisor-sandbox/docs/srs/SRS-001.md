# SRS-001 — Sandboxed Tool Execution (gVisor)

**Project:** P07 — Sandboxed Tool Execution (gVisor)
**Version:** 1.0
**Date:** 2026-08-07
**Status:** Draft
**Author:** David Scheiderman

---

## 1. Purpose

This document specifies the requirements for integrating gVisor (`runsc`) as an opt-in sandboxed execution mode for untrusted agent-generated code and MCP tool calls inside Orchid, a self-hosted agent orchestration platform. This is an integration and hardening project on top of gVisor's existing runtime — not a from-scratch sandbox — wired into Orchid's `TesterAgent` lifecycle alongside its existing `verify_syntax_only` mode.

## 2. Scope

**In scope:**
- A sandbox execution API that accepts untrusted code/commands and returns bounded results
- `runsc` installed and configured as a secondary Docker runtime on the NucBox EVO X2 host
- Resource ceilings (timeout, memory, CPU) enforced per execution
- Default-deny network egress with explicit allowlist mode
- A new `sandboxed_execution` mode on Orchid's `TesterAgent`, additive to `verify_syntax_only`
- Per-execution syscall observability
- A stretch demonstration of per-tenant resource quotas

**Out of scope:**
- Building a new container runtime or sandbox technology
- Replacing Docker as Orchid's primary execution substrate
- GPU-passthrough or ROCm workloads inside the sandbox (v1)
- Auth or multi-user exposure of the execution API (host-local only, v1)

## 4. Functional Requirements

### FR-1 — Isolated Runtime Execution

**Statement:** Code submitted for sandboxed execution shall run inside a `runsc`-isolated container rather than the default Docker runtime.

**Acceptance criteria:**
- `docker run --runtime=runsc` executes successfully alongside existing default-runtime containers on the NucBox
- Isolation is verified via at least one syscall-interception test, with output documented

**Related:** ADR-001

### FR-2 — Bounded Execution API

**Statement:** A thin execution service shall accept a code-execution request and return a bounded result, enforcing timeout and memory limits.

**Acceptance criteria:**
- Request shape: `{code, language, timeout_s, memory_mb, network}`
- Response shape: `{stdout, stderr, exit_code, duration_ms}`
- Execution exceeding the timeout is killed and returns a structured error
- Execution exceeding the memory limit is killed and returns a structured error
- A known test script returns correct `stdout`/`stderr`/`exit_code`

### FR-3 — Default-Deny Network Policy

**Statement:** Sandboxed executions shall have no network access by default; access to specific domains shall be grantable via explicit allowlist.

**Acceptance criteria:**
- Default execution has zero network access, verified via a failed `curl` attempt inside the sandbox
- Allowlisted execution can reach only the specified domain(s), confirmed via test
- Allowlist mode routes through the existing Traefik/proxy configuration

### FR-4 — Orchid `TesterAgent` Integration

**Statement:** Orchid's `TesterAgent` shall support a new `sandboxed_execution` mode, additive to the existing `verify_syntax_only` mode, using the existing task/result schema.

**Acceptance criteria:**
- `TesterAgent` can be configured to run in `sandboxed_execution` mode without breaking `verify_syntax_only`
- Results appear in PM Dashboard using the existing task metrics display, with no schema break

**Related:** ADR-002

### FR-5 — Per-Execution Syscall Observability

**Statement:** Each sandboxed execution shall produce a retrievable syscall log associated with its task ID.

**Acceptance criteria:**
- Each sandboxed execution has an associated syscall log retrievable by task ID
- At least a summary view is visible in ccview or the PM Dashboard

### FR-6 — Multi-Tenant Resource Quotas (Stretch)

**Statement:** The system shall demonstrate independently enforced resource quotas for at least two concurrent "tenants."

**Priority:** Stretch — pursued only after FR-1 through FR-5 are demoable.

**Acceptance criteria:**
- Two concurrent tenants run with independently enforced cgroup-based quotas, demonstrated concurrently

## 5. Non-Functional Requirements

### NFR-1 — Schema Compatibility

The execution API and `sandboxed_execution` mode must reuse Orchid's existing task/result schema. No parallel result format may be introduced.

**Related:** ADR-002

### NFR-2 — Deployment Scope

The execution API is host-local for v1. No authentication or multi-user exposure is required or in scope.

**Related:** ADR-003

### NFR-3 — Runtime Coexistence

Installing `runsc` must not disrupt any existing default-runtime container on the NucBox Docker/Traefik stack.

**Related:** ADR-001

### NFR-4 — Portfolio Demo Scale

The system is a portfolio proof, not a production or load-tested service. The multi-tenant quota demonstration (FR-6) is scoped to two concurrent tenants, not a sizing exercise.

## 7. Assumptions

- The Orchid repository is available on the NucBox for extension (new module, e.g. `orchid/sandbox/`)
- The NucBox host kernel and Docker version support `runsc` (confirmed in Phase 0 recon)
- The existing Traefik configuration is accessible for later egress-allowlist wiring
