# SRS-001 — Sandboxed Tool Execution (gVisor)

**Project:** P07 — Sandboxed Tool Execution (gVisor)
**Version:** 1.1
**Date:** 2026-08-07
**Status:** Draft
**Author:** David Scheiderman

---

## 1. Purpose

This document specifies the requirements for hardening Orchid's existing container-based task isolation with gVisor (`runsc`), enforced resource ceilings, and default-deny network egress. Orchid already isolates agent task execution generically via `ContainerRunner` (config: `isolation.container_enabled`) — this project hardens that existing mechanism rather than building a new sandbox execution service. This is an integration and hardening project on top of gVisor's existing runtime, not a from-scratch sandbox.

**Revision note (v1.1):** Rewritten after Phase 0 recon (2026-08-07) found the real Orchid codebase — `ContainerRunner`, `WorkerResult`/`TaskContext`, and the generic `isolation.*` config layer — does not match this document's original assumptions (a new `TesterAgent` "mode" and a `{code, language, timeout_s, memory_mb, network}` → `{stdout, stderr, exit_code}` service). See `findings.md` for the full audit and the decision to harden `ContainerRunner` in place. v1.0 is preserved in git history.

## 2. Scope

**In scope:**
- `runsc` installed and configured as a secondary Docker runtime on the NucBox EVO X2 host
- A new `isolation.container_runtime` config option (default: unset / `runc`) on `ContainerRunner`, selectable to `runsc`
- Resource ceilings (memory, CPU) added to `ContainerRunner`'s `docker run` invocation — none exist today
- Default-deny network egress (`--network none`) with explicit allowlist mode added to the same invocation
- `WorkerResult` extended additively with optional fields (e.g. `stdout`, `stderr`, `exit_code`) — no parallel result schema
- Per-execution syscall observability
- A stretch demonstration of per-tenant resource quotas

**Out of scope:**
- Building a new container runtime or sandbox technology
- Replacing Docker as Orchid's primary execution substrate
- A new standalone "Sandbox Execution API" service — superseded by hardening `ContainerRunner` directly
- Per-language sandbox base images — `ContainerRunner` runs one fixed image (`python:3.12-slim`) executing Orchid's own worker module, not arbitrary user-selected-language snippets
- GPU-passthrough or ROCm workloads inside the sandbox (v1)
- Auth or multi-user exposure — sandboxed execution is invoked locally via `ContainerRunner`, not through the existing `remote/worker_server.py` FastAPI service (which binds all interfaces and is out of scope for this project)

## 4. Functional Requirements

### FR-1 — Isolated Runtime Execution

**Statement:** Containerized task execution shall run inside a `runsc`-isolated container rather than the default Docker runtime, when configured.

**Acceptance criteria:**
- `docker run --runtime=runsc` executes successfully alongside existing default-runtime containers on the NucBox
- Isolation is verified via at least one syscall-interception test, with output documented

**Related:** ADR-001

### FR-2 — Hardened `ContainerRunner`

**Statement:** `ContainerRunner`'s `docker run` invocation shall support selecting the `runsc` runtime and enforcing memory/CPU limits, gated by config.

**Acceptance criteria:**
- New config keys under `isolation.*` (e.g. `isolation.container_runtime`, `isolation.container_memory_mb`, `isolation.container_cpus`) control the `docker run` flags `--runtime`, `--memory`, `--cpus`
- Execution exceeding the memory limit is killed by Docker/the kernel OOM path and surfaces as a failed `WorkerResult` (`success=False`, `error` populated)
- Execution exceeding `timeout_s` (already enforced today via `subprocess.Popen`/`proc.wait(timeout=...)` in `ContainerRunner.run_task_isolated`) continues to kill the container and return a structured error — unchanged by this work
- A known test task returns a correct `WorkerResult` when run under `--runtime=runsc` with limits applied

**Related:** ADR-002

### FR-3 — Default-Deny Network Policy

**Statement:** Sandboxed executions shall have no network access by default; access to specific domains shall be grantable via explicit allowlist.

**Acceptance criteria:**
- Default execution runs with `--network none`, verified via a failed `curl` attempt inside the container
- Allowlisted execution can reach only the specified domain(s), confirmed via test
- Allowlist mode routes through the existing Traefik/proxy configuration

### FR-4 — Additive `WorkerResult` Fields

**Statement:** `WorkerResult` shall be extended with optional fields carrying process-level execution detail, without altering its existing fields or breaking any existing consumer.

**Acceptance criteria:**
- `WorkerResult` gains optional fields (default unset/empty) — e.g. `stdout`, `stderr`, `exit_code` — populated when `ContainerRunner` has that detail available
- All existing `WorkerResult` consumers (`orchestrator.py`, `remote/worker_server.py`, `remote/dispatcher.py`, `worker_subprocess.py`) continue to work unmodified — verified by running Orchid's existing test suite for these modules with no failures
- No second/parallel result schema is introduced

**Related:** ADR-002

### FR-5 — Per-Execution Syscall Observability

**Statement:** Each sandboxed execution shall produce a retrievable syscall log associated with its task ID.

**Acceptance criteria:**
- Each sandboxed execution has an associated syscall log retrievable by task ID
- At least a summary view is visible in ccview or the PM Dashboard

### FR-6 — Multi-Tenant Resource Quotas (Stretch)

**Statement:** The system shall demonstrate independently enforced resource quotas for at least two concurrent "tenants."

**Priority:** Stretch — pursued only after FR-1 through FR-5 are demoable.

**Acceptance criteria:**
- Two concurrent tenants run with independently enforced cgroup-based quotas, demonstrated concurrently

## 5. Non-Functional Requirements

### NFR-1 — Schema Compatibility

Hardening must reuse and extend Orchid's existing `WorkerResult`/`TaskContext` schema additively. No parallel result format may be introduced.

**Related:** ADR-002

### NFR-2 — Deployment Scope

Sandboxed execution is invoked locally through `ContainerRunner`/`SubprocessRunner`, not exposed via `remote/worker_server.py` or any other network-bound service. No authentication or multi-user exposure is required or in scope.

**Related:** ADR-003

### NFR-3 — Runtime Coexistence

Installing `runsc` must not disrupt any existing default-runtime container on the NucBox Docker/Traefik stack. `isolation.container_runtime` must default to the existing behavior (`runc`) when unset, so existing deployments are unaffected until explicitly opted in.

**Related:** ADR-001

### NFR-4 — Portfolio Demo Scale

The system is a portfolio proof, not a production or load-tested service. The multi-tenant quota demonstration (FR-6) is scoped to two concurrent tenants, not a sizing exercise.

## 6. Constraints

| Constraint | Description |
|------------|--------------|
| Host OS | Requires Linux with `runsc` support; does not run on the portfolio author's macOS dev machine |
| Execution host | NucBox EVO X2 homelab host, alongside the existing Docker/Traefik stack |
| Upstream dependency | Depends on Orchid's existing `ContainerRunner`, `WorkerResult`/`TaskContext`, and `isolation.*` config, defined outside this repo |
| Fixed base image | `ContainerRunner` runs a single fixed image (`python:3.12-slim`); this project does not add per-language image selection |
| Sequencing | Must reach at least Phase 4 before P08 (Firecracker) begins, per the shared execution result contract |

## 7. Assumptions

- The Orchid repository is available on the NucBox for extension (`orchid/container_runner.py`, `orchid/worker_protocol.py`)
- The NucBox host kernel and Docker version support `runsc` — confirmed in Phase 0 recon (`runsc release-20260803.0` verified against kernel `6.19.0-061900rc8-generic`)
- The existing Traefik configuration is accessible for later egress-allowlist wiring (candidate config files identified in Phase 0 recon, not yet confirmed which governs sandbox egress)
